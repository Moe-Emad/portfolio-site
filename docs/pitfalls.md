# Pitfalls

Problems that cost time once. Add a row with the date whenever a problem costs time (an environment trap, a tool
quirk, a mistake), so it never costs time twice.

| # | Symptom | Cause | What to do |
|---|---|---|---|
| 1 | The build passes on this PC and fails on GitHub or on a host with "Could not resolve ../components/models/..." | Windows ignores the letter case of file names, Linux does not. An import written as `models` finds the folder `Models` only on Windows. (2026-11-17) | Write import paths with the exact case of the folder and file. The CI gate builds on Linux and catches it. |
| 2 | `.env` shows up in `git status`, or was committed | A `.gitignore` without a `.env` line lets the file with the EmailJS settings be committed like any other. (2026-11-17) | `.env` is git-ignored here and the pre-commit hook refuses it. Settings go in `.env`; only names go in `.env.example`. |
| 3 | A git hook fails with `/bin/sh^M: bad interpreter` or does nothing | Git on this PC has `core.autocrlf=true` and would check the hook files out with Windows line endings. (2026-11-17) | `.gitattributes` forces LF for `.githooks/*` and shell scripts. Do not remove those lines. |
| 4 | A command from the docs fails in PowerShell with "The token '&&' is not a valid statement separator" | PowerShell 5.1 has no `&&`. (2026-11-17) | Give one command per line, or join with `;`. Never bash syntax in the docs. |
| 5 | A script that edits a file by exact text finds nothing, or every commit prints "LF will be replaced by CRLF" | Git on this PC has `core.autocrlf=true` and checked text files out with Windows line endings, so the same file had different bytes on Windows and on GitHub. (2026-11-17) | `.gitattributes` says `* text=auto eol=lf`: LF everywhere. After changing that file, refresh the working folder once with `git add --renormalize .` |
| 6 | Playwright says the browser is missing and wants to download another Chromium, although one is installed | `@axe-core/playwright` asks for any `playwright-core`, and npm then installs the newest one next to the pinned `@playwright/test`: two Playwright versions, two browsers. (2026-11-17) | `playwright-core` is a dev dependency pinned to the same exact version as `@playwright/test`; a test checks it. Move both together. |
| 7 | The axe browser test passes on the PC and runs into the time limit on GitHub | A GitHub runner has no graphics card. The three WebGL scenes of the original page are drawn by the processor there and keep the page so busy that timers stall and animations never finish. (2026-11-17) | Solved by F2, which removed the scenes: every browser test runs on GitHub again. The lesson: when a test is slow only on the runner, look at what the page does before raising a time limit. |
| 8 | A failing test run looked green, and a broken change was pushed | The command was piped into `tail` or `grep` to shorten its output; a pipe reports the exit code of its last command, so the failure was swallowed. (2026-11-17) | Write the output to a file, print the exit code of the command itself, then read the file. Never judge a run by filtered output alone. |
| 9 | A link to a section of another page (`/#contact`) opens the page at the top | The page is drawn by JavaScript after the browser has looked for the section, so there was nothing to scroll to. (2026-11-17) | `App.tsx` scrolls to the section of the address once the page is drawn; a browser test follows such links from a project page. |
| 10 | The hook tests pass on this PC and fail on GitHub: "the commit went through", "the push to main went through" | Files copied in on Windows (here with `git archive` and `tar`, D4) were added without the executable mark. Windows runs a hook anyway; Linux skips a hook that is not executable. (2026-11-19) | `git ls-files -s .githooks` must show `100755`; set it with `git update-index --chmod=+x <file>`. The hook tests on GitHub catch it. |
| 11 | A dependency update fails the lock check with "does not come from the npm registry (no address)" and "has no sha512 checksum" for packages under another package's `node_modules` | They are bundled: they come inside the download of the package above them (`"inBundle": true` in `package-lock.json`), so npm gives them no address or checksum of their own. Tailwind CSS 4.3 brought the first ones. (2026-11-19) | Since A7 the check accepts a bundled package whose carrier is in the lock file. If it reports one again, look for `inBundle` and its carrier before suspecting the registry. |
| 12 | After a merge the next branch starts from the merged item's branch instead of `main`, and that branch is not deleted | `gh pr merge --squash --delete-branch` merges on GitHub, then switches to `main` on this PC. Uncommitted work in a file that differs between the two branches stops that switch: the merge went through, but the local and the remote branch stay, and the next `git switch -c` starts from the old branch. (2026-11-20) | Commit or stash all work before merging. Afterwards check `git branch --show-current` and that `git log -1` matches `origin/main` before starting the next branch. |
| 13 | A rule of the stylesheet has no effect in the built site, although it works with `npm run dev` | The minifier of the build (Lightning CSS, inside Vite) writes the shorthand `border-image: none` as `border-image:` with no value, which the browser drops. Found when a print rule did nothing (F48). (2026-11-20) | Write the longhand (`border-image-source: none`). When a rule seems ignored, look for it in `dist/assets/*.css` before blaming the selector. |
| 14 | The corner test finds a rule for a class that no component uses, with `border-radius: 0.25rem` | Tailwind CSS looks for class names in every file of the project that git does not ignore: tests, docs and comments included. One plain English word for curved corners, which is also the name of a Tailwind class, in a comment of a browser test made it write that class into the site's stylesheet (F50); writing the class name in this row did it again. (2026-11-20) | When a test reports a rule nobody wrote, search the whole project, docs included, for its class name as a plain word, and reword the text that holds it. |
| 15 | A browser test that compares two fonts by their pixels passes although one of them lacks a letter | Two causes, each enough to draw both texts in the same stand-in font: the test page was a page of the site, whose Content-Security-Policy (`font-src 'self'`) refuses fonts given as `data:`; and `document.fonts.ready` resolves at once when no font has started to load. Found in F56, when a font cut down on purpose without one letter still passed. (2026-11-20) | Draw on `about:blank`, load the fonts with `document.fonts.load()`, and check that the font in question draws differently from the stand-in before comparing. Prove such a test with a deliberate defect. |
